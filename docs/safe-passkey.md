# Сейф: смена пароля с подтверждением доверенным ключом

## Модель угроз

Школьный ПК и его MAX-сессия считаются недоверенными. Вход в MAX, наличие
access JWT и даже действующий X-Safe-Token не дают права сменить пароль Сейфа.
Сообщение от MAX — только уведомление. Кнопки MAX не подтверждают смену.

## Привязка ключа (однократно)

На личном телефоне откройте Смену внутри MAX, зайдите в Сейф и выберите
«Привязать телефон». Введите **текущий** пароль Сейфа и подтвердите создание
WebAuthn passkey с проверкой владельца (PIN/биометрия). Сервер хранит
публичный ключ и счётчик, не приватный ключ. Уже привязанный ключ нельзя
заменить обычной MAX-сессией. При утере телефона требуется отдельная
проверенная процедура восстановления **вне школьного ПК**; API не имеет
запасного «сбросить по MAX» пути.

Если браузер внутри MAX не поддерживает WebAuthn, операция завершается
отказом. Поддержку MAX WebView на iOS и Android нужно проверить на реальных
устройствах до внедрения в школах.

## Смена пароля

1. На любом устройстве преподаватель нажимает «Запросить смену пароля».
2. Сервер создаёт один ожидающий запрос на 5 минут и отправляет сообщение
   бота MAX. Повторные запросы ограничены: не чаще одного в минуту.
3. На доверенном телефоне преподаватель открывает Смену, вводит **новый**
   пароль и подтверждает действие ранее привязанным passkey.
4. Сервер проверяет challenge, RP ID, HTTPS origin, подпись и user verification.
   Только затем обновляет scrypt-хеш пароля и увеличивает
   users.safe_password_version. Все ранее выданные Safe-токены теряют силу.
5. Повторное подтверждение старого запроса невозможно.

Пароль никогда не пересылается в MAX, а подтверждение через чат не принимается.
Неправильные попытки ввода пароля Сейфа ограничены: 5 ошибок — 15 минут
блокировки; ограничение действует также при привязке ключа.

## Ограничения безопасности

WebAuthn с authenticatorAttachment=platform и userVerification=required
подтверждает владение ключом и локальную проверку пользователя, **но не
доказывает**, что устройство физически является телефоном. Некоторые passkey
синхронизируются облаком на другие устройства. Для строгой гарантии
«только конкретный физический телефон» потребуется проверенная
device-bound реализация с аттестацией/MDM либо собственное мобильное
приложение с аппаратно защищённым ключом и attestation. User-Agent
проверяется только для интерфейса и не является мерой безопасности.

Первая установка пароля Сейфа в старой версии выполняется через MAX-сессию.
Это отдельный bootstrap-риск, если владелец ещё не создавал пароль и оставил
сессию на школьном ПК. Для высокозащищённого развёртывания первичную
активацию нужно переносить в проверенную процедуру на личном устройстве.

Пароль Сейфа сам по себе не защищает уже открытые материалы на оставленном
компьютере. Нужны блокировка по отсутствию и отзыв разрешений.

## Развёртывание

В production Compose автоматически задаёт:

- PASSKEY_RP_ID из APP_DOMAIN;
- PASSKEY_ORIGIN как https://APP_DOMAIN;
- MAX_BOT_TOKEN — существующий секрет бота.

После обновления API обязательно применить Alembic migration
20261108_a1c0. Сделайте резервную копию PostgreSQL перед миграцией.

GitHub main и ветка VPS исторически расходятся. **Не используйте**
git reset --hard или git pull --ff-only для прямого обновления. Сначала
разрешите расхождение, а затем применяйте согласованный набор коммитов:
для этой функции нужны изменения backend, frontend, Compose и миграции.

Проверка: ruff, mypy, pytest, npm typecheck, npm test, npm build и
проверка WebAuthn на настоящем телефоне через MAX.
